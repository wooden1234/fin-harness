# 传闻核验 使用指南

## 技能概述

本技能用于核验单条传闻或消息的真实性，支持：

- **拆解传闻**：主体、事件、时间、可证伪陈述
- **确认路径**：公告/监管披露优先，独立报道次之
- **状态判定**：确认 / 否认 / 未证实三态，不强行二选一
- **影响评估**：核验后再补相关行情，不用传闻本身替代行情证据

## 核心处理流程

### 步骤 0: 规划 todos（调工具前）

传闻/政策/「还能上车」类题先写 3–5 条 todos：题意改写（如预期发酵 vs 业绩兑现）、待核验陈述、取证主路径（公告优先，政策主题可分槽位 Web）、行情验证、成稿约束（敏感题只给条件与风险、不给买卖指令）。禁止空泛「搜索一下」。

### 步骤 1: 拆解传闻

把用户描述的传闻拆成四要素：主体（公司/人物/行业主题）、事件（做了什么）、时间（何时发生或披露）、可证伪陈述（能被证据直接证实或证伪的具体说法，而非笼统情绪判断）。

### 步骤 2: Query 改写

**改写规则：**

- 带上主体、事件关键词和时间，避免只搜主体名导致结果宽泛
- 监管/公司事件：优先 `search_iwencai_announcement`；公告未命中或需要独立信源时用 `search_web`
- 行业政策/审批节奏等主题（公告工具难覆盖）：规划后可直接分槽位 `search_web`（如政策、在建/装机、机构观点），每次 query 对准一个槽位并声明 entities；再视需要补 `query_iwencai_market`
- **`search_web` 问句润色（调工具前完成）**：把口语改成可检索短语——保留主体/事件/年份，删掉买卖动作与情绪词；一槽位一句，长度约 8–20 字为宜；空结果时可放宽表述 **最多 1 次**（如去掉过细时间），不无限改写

**常用查询改写示例：**

| 用户原始传闻 | 改写后查询（可分多次调用） |
|-------------|---------------------------|
| 听说 A 公司要被 B 收购了 | A公司 B公司 收购 公告 |
| C 公司是不是要退市 | C公司 退市 监管 公告 |
| D 产品出问题了是真的吗 | D公司 D产品 事件 公告 声明 |
| 核电项目审批提速，现在还能上车吗？ | `2026年核电项目审批提速 政策`；`2026年核电机组 在建 装机目标`；`核电板块 机构观点 研报`（禁止把「还能上车」写入 query） |
| 苹果微软谷歌最近财年收入并引用来源 | 财务走问财分年结；Web 出处例：`苹果 FY2025 年报 营业收入`（一司一句，勿三家糊成一句） |

### 步骤 3: 核对与判定

1. 核对返回内容中的目标实体、事件、日期是否与传闻一致；同名主体、零命中、与传闻事件无关的结果不作为确认依据。
2. 同时寻找支持与反方证据（如官方否认、监管澄清），不能只采信单一方向的信息。
3. 按证据强度判定：
   - **已确认**：有公告、监管披露或官方声明直接对应
   - **已否认**：公司/监管有明确澄清或辟谣
   - **未证实**：仅有传闻或单一非官方信源，缺乏可核验的官方来源

### 步骤 4: 补充影响评估（可选）

仅在用户关心市场影响、且传闻已达到「确认」或「未证实但有明显行情反应」时，才用 `query_iwencai_market` 补一次行情数据；不用短期涨跌本身反证传闻真假。

## 注意事项

- 空结果或串台结果不近义改写连打；放宽 1 次仍无结果即判定未证实并写明已查过的来源。
- 不把传闻、市场情绪或短期行情解释为确定收益、确定交易指令，或作为传闻真伪的直接证据。
- 涉及并购、监管等敏感事件时，优先引用官方原文措辞，避免转述失真。
