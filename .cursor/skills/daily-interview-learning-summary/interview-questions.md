## A. 系统全貌

### Q1. 端到端链路 + Agent Harness

**合并原题**：1, 13

**主问题**：从输入任务到最终修改/输出，完整链路是怎样的？Agent Harness 和裸调 LLM API 的区别是什么？

**答题骨架**：
- **一句话结论**：Harness = 编排 + 状态 + 工具 + 校验 + 可观测，不是单次 prompt。
- **口述结构**：输入 → guardrails/校验 → 上下文治理 → 路由/规划 → 子图或 worker 执行 → join/汇总 → 最终输出。
- **本项目锚点**：`app/agents/graph.py`（主图）；`finance_agent/graph.py`（子图 planner → workers → join → summarize）。
- **与裸 API 差异**：有状态机、条件边、短路、子图封装、失败不直接暴露给用户。

**常见追问**：
- 为什么主图只暴露一个 `plan_agent` 节点？→ 子图对内复杂、对外接口简单。
- 状态存在哪？→ LangGraph checkpoint（若今日涉及再展开）。

**映射档**：本项目

## B. 模型与工具

### Q2. 工具系统全流程 + 失败恢复

**合并原题**：2, 3, 4

**主问题**：一个新工具从定义、注册、被 Agent 发现，到被调用，完整流程是什么？调用失败（文件不存在、超时、权限不足）时怎么处理？

**答题骨架**：
- **定义**：输入 schema、权限、超时、错误语义。
- **注册**：工具 registry / 节点绑定 / MCP 或 function calling 声明。
- **发现**：planner 或 supervisor 根据意图选 worker；LangGraph 节点即「可调用单元」。
- **调用**：隔离执行（如 `isolate_worker_node`）→ 结构化返回 → join 汇总。
- **失败恢复**：区分可重试（超时、限流）vs 不可重试（权限、不存在）；返回错误给 planner 换路径，而非整链崩溃。

**常见追问（原题 2）**：多模型后端怎么抽象？
- 统一 Request/Response 适配层；错误码映射；按错误类型重试（429/5xx 退避，4xx 不重试）；模型能力标签供路由选择。

**本项目锚点**：`workers/isolation.py`；各 worker 节点；`app/core/` LLM 客户端（若存在）。

**映射档**：本项目（worker/编排）+ 方法论（通用 tool registry）

## C. 上下文工程

### Q3. 上下文压缩与约束保真

**合并原题**：5, 6, 7, 8

**主问题**：多轮任务上下文变长时怎么处理？压缩后如何保证不破坏当前任务、不遗漏关键约束？

**答题骨架**：
- **场景**：对话历史 + 工具输出 + 文件片段累积，逼近 context 上限。
- **策略**：分层摘要——任务摘要 / 文件摘要 / 过程笔记；保留最近 N 轮原文 + 结构化约束块（目标、未完成项、禁止项）。
- **校验**：压缩后对照检查清单——当前目标、打开文件、待改模块、测试命令是否仍在；必要时 re-read 关键文件。
- **遗漏修正**：下游行为异常 → 对比摘要与 git diff / 用户原约束 → 补写约束或触发 re-read。

**常见追问**：
- 摘要怎么生成？→ 按轮次增量更新，关键约束单独字段不进入自由摘要。
- 如何避免压掉关键信息？→ 白名单字段（任务目标、API 签名、测试命令）不参与压缩。

**本项目锚点**：`app/agents/components/context_compressor/`；主图在 supervisor 前执行压缩。

**映射档**：本项目（compressor 节点）+ 方法论（校验清单、约束白名单）

## D. 记忆与纠错

### Q4. 记忆污染、错误结论与重复状态

**合并原题**：9, 10, 11

**主问题**：长期记忆里的过时摘要或错误结论怎么发现与纠错？多轮执行中如何识别重复读文件、重复调工具？

**答题骨架**：
- **污染类型**：过时文件摘要、错误函数理解、重复失败路径。
- **发现**：摘要有 version/timestamp；关键判断要求 re-read 源文件；工具调用带 call_id 去重。
- **纠错**：用户纠正 / 测试失败 / diff 与摘要矛盾 → 标记记忆失效或版本递增；错误结论不写入长期记忆，只写 verified 事实。
- **重复状态**：维护「本轮已读文件」「已执行命令」集合；相同输入+相同工具 → 短路或提示 planner 换策略。

**常见追问**：
- 误判函数作用后一直错怎么办？→ 短期：强制 re-read；长期：记忆带来源与置信度，测试失败自动降级。

**本项目锚点**：LangGraph state / checkpoint（按实际实现表述）；worker 隔离避免交叉污染。

**映射档**：方法论为主；本项目仅在有 checkpoint/state 设计时展开

## E. 质量闭环

### Q5. 评测体系

**原题**：14

**主问题**：有没有评测体系？怎么设计 benchmark、case、指标？如何判断一次改动真的让 Agent 变强了？

**答题骨架**：
- **分层**：单元（单节点 prompt/路由）、集成（子图端到端）、回归（golden case）。
- **指标**：任务成功率、工具调用次数、延迟、幻觉率、人工抽检 pass rate。
- **对比**：改动前后同一 case 集 A/B；固定 seed；记录 diff 与失败类型分布。
- **防自嗨**：case 来自真实失败日志，不只 hand-pick 简单题。

**本项目锚点**：`planner/eval_cases.py`（若今日涉及）；predefined registry 白名单覆盖度。

**映射档**：本项目（局部 eval）+ 方法论（完整 benchmark 平台）

### Q6. 错误 patch 与跨模块改动

**合并原题**：15, 19

**主问题**：Agent 生成错误修改时怎么回滚、验证、再尝试？大型仓库跨模块改动时，如何先理解架构再动手？

**答题骨架**：
- **回滚**：git stash/checkout；不 commit 错误 patch；保留失败上下文供下一轮。
- **验证**：测试 / lint / 类型检查 / 最小复现；通过才保留改动。
- **再尝试**：缩小 patch 范围；先读再改；单文件单职责提交。
- **大仓策略**：架构检索（README、graph、入口）→ 依赖 grep → 列影响面 → 分步改 → 每步验证。

**常见追问（原题 19）**：
- 检索：符号定义、调用链、模块边界；规划：先接口契约再实现；验证：受影响模块测试全跑。

**映射档**：个人实践（Cursor + git）+ 方法论（自动化 patch 验证）

### Q7. RAG / Memory / Context Engineering

**原题**：12

**主问题**：RAG、Memory、Context Engineering 分别解决什么问题？在你的 Agent 里如何配合？

**答题骨架**：
| 概念 | 解决什么 | 本项目对应 |
|------|----------|------------|
| **RAG** | 外部知识检索，补模型不知道的 fact | `app/retrieval/`、faq/pdf/web worker |

- **配合**：RAG 进 worker → 结果进 state → compressor 控窗口 → Memory 存 verified 结论。

**映射档**：本项目

### Q8. 个人 AI 工作流 + 团队化安全

**合并原题**：16, 17, 18

**主问题**：一个需求你怎么用 AI 辅助完成？若做成团队工具，权限、安全、审计怎么处理？

**答题骨架（个人流）**：
1. 拆需求：目标、边界、验收标准
2. 读代码：入口 → 调用链 → 相关测试
3. 改代码：小步 patch，一次一个 concern
4. 跑测试：失败日志反馈给模型
5. Review：diff + 行为是否符合约束

**答题骨架（团队化，原题 18）**：
- 文件读写：路径白名单、只读/读写分级
- 命令执行：allowlist、沙箱、无 root
- 敏感信息：secret 扫描、日志脱敏、审计流水
- 审计：谁、何时、调了什么工具、改了什么文件

**本项目锚点**：`guardrails/`、`risk_triage/`（合规拦截）；`app/api/` 暴露边界。

**映射档**：个人实践 + 本项目（guardrails）+ 方法论（完整审计平台）
