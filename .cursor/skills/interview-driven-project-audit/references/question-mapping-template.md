# 单题映射与改进项模板

## 单题映射表（§3 使用）

每道去重后的面试题填一行：

```markdown
| 面试问题 | 考察能力 | 项目证据 | 证据强度 | 当前状态 | 缺口 |
|----------|----------|----------|----------|----------|------|
| [公司A/B] 工具调用失败怎么处理？ | 工具失败恢复（主） | `predefined/node.py` L41-50 `_fallback_to_text_to_sql` | B | 部分支持 | 无重试；无统一错误分类；缺集成测试 |
```

### 字段说明

| 字段 | 要求 |
|------|------|
| 面试问题 | 保留原文要点；多来源用 `[公司]` 前缀 |
| 考察能力 | 12 维度之一；多维度写「主/次」 |
| 项目证据 | 具体文件路径 + 符号/行号；无则写「检索范围：…，未找到」 |
| 证据强度 | A / B / C / D（见 evaluation-rubric.md） |
| 当前状态 | 六种状态之一 |
| 缺口 | 一句话，可检验 |

### 无证据时的写法

```markdown
| [海天] Agent 如何做 loop 检测？ | 重复状态识别 | 检索：`app/agents/`, `guardrails/`；未找到 loop detector | D | 待验证 | 需确认是否通过 max_iterations 间接实现 |
```

**禁止**写成「项目不支持 loop 检测」——应写「待验证」或「缺失」（仅当检索充分时）。

## 改进项模板（§4/5/6 使用）

每个 P0/P1/P2 项复制此结构：

```markdown
### [P0-01] 标题：简短动宾短语

**对应面试题**
- [快手] xxx
- [海天] yyy（合并）

**当前项目现状**
- 证据：`path/to/file.py` — 简述已有行为
- 证据强度：B

**缺少什么**
- 缺测试 / 缺文档 / 缺降级策略 / …（具体、可验证）

**建议修改的模块或文件**
- `app/agents/...`
- `tests/...`
- `docs/...`

**推荐实现方案**
1. 第一步：…
2. 第二步：…
3. 避免过度设计：…

**应补充的测试**
- 单测：`test_xxx.py` — 覆盖场景
- 集成测：…

**完成验收标准**
- [ ] 条件 1（可客观检查）
- [ ] 条件 2

**面试表达（完成后）**
> 在我们金融 Multi-Agent 平台里，当 predefined 工具选择失败时，会自动降级到 text-to-sql 路径。我补充了集成测试覆盖这个 fallback，并记录了降级原因到 state，面试时可以画一张 planner → predefined → fallback 的流程图说明。

**优先级依据**
- 面试频率：高（3 家公司）
- 实现成本：低（约 2 文件）
- 依赖：无
```

## 归类速查：面试题关键词 → 维度

| 关键词 / 问法 | 优先维度 |
|---------------|----------|
| 链路、流程、状态机、LangGraph | Agent 完整执行链路 |
| 多模型、换模型、GPT/Claude | 多模型适配 |
| tool、函数调用、schema | 工具定义、注册和调用 |
| 失败、重试、降级、fallback | 工具失败恢复 |
| 上下文、压缩、token、摘要 | 上下文治理和压缩 |
| RAG、向量、记忆、检索 | Memory、RAG 和 Context Engineering |
| 死循环、重复调用、loop | 重复状态识别 |
| Harness、边界、沙箱、钩子 | Agent Harness |
| 评测、benchmark、黄金集 | Benchmark 和评测体系 |
| patch、diff、回滚、验证 | Patch 验证与回滚 |
| Cursor、Skill、AI 写代码 | AI 辅助开发流程 |
| 权限、安全、审计、鉴权 | 权限、安全和审计 |
| 大仓、跨模块、重构 | 大型代码仓库理解与跨模块修改 |

一题命中多关键词时，选**面试官最可能追问**的维度为主维度。
