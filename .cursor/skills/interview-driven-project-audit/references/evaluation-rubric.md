# 能力评估与归类细则

## 12 个能力维度定义

### 1. Agent 完整执行链路

**定义**：从用户输入到最终输出的端到端路径，含规划、路由、执行、汇总、错误分支。

**证据检索**：
- `app/agents/graph.py`、子图入口、`planner`、`workflow`
- state 定义（`FinAgentState` 等）
- `steps` 字段、流式进度回调

**已完整支持**：主路径可跑通 + 有失败分支 + 文档或测试覆盖关键节点。

---

### 2. 多模型适配

**定义**：不同节点使用不同 LLM、结构化输出、模型配置切换。

**证据检索**：
- `get_router_llm`、`get_*_llm`
- `with_structured_output`、`bind_tools`
- 环境变量 / 配置中的 model 字段

---

### 3. 工具定义、注册和调用

**定义**：Tool schema 定义、注册到 LLM、参数解析、调用执行。

**证据检索**：
- `bind_tools`、`PydanticToolsParser`
- `predefined/tool_selection`、`execution`
- tool 模型类（如 `predefined_sql`）

---

### 4. 工具失败恢复

**定义**：tool 调用失败后的重试、降级、fallback、错误信息回传。

**证据检索**：
- `fallback_to_text_to_sql`、`_fallback_slots`
- try/except 包裹的 tool 调用
- 重试逻辑、超时处理

**部分支持常见表现**：有 fallback 但无重试；有日志但无用户可感知降级说明。

---

### 5. 上下文治理和压缩

**定义**：对话历史管理、token 预算、摘要压缩、checkpoint 持久化。

**证据检索**：
- compressor、summarize、trim
- LangGraph checkpoint 配置
- `map-reduce`、上下文窗口相关文档

---

### 6. Memory、RAG 和 Context Engineering

**定义**：向量检索、混合问答、长期记忆、prompt 组装策略。

**证据检索**：
- `app/retrieval/`
- `docs/rag/`
- embedding、vector store、hybrid QA 实现

---

### 7. 重复状态识别

**定义**：检测 Agent 循环、重复 tool call、无效状态跳转并恢复。

**证据检索**：
- 循环检测、max_iterations
- 相同 tool 连续调用拦截
- guardrails 中的重复输入检测

---

### 8. Agent Harness

**定义**：平台边界、子图隔离、钩子、权限约束、可观测性基础设施。

**证据检索**：
- `docs/architecture/harness-and-tools.md`
- `.cursor/hooks/`
- 子图接入方式、工具白名单

---

### 9. Benchmark 和评测体系

**定义**：黄金问题集、自动化回归、指标统计、基线对比。

**证据检索**：
- `tests/` 中的集成测试、eval 脚本
- `benchmark/`、`eval/` 目录
- CI 中的评测步骤

---

### 10. Patch 验证与回滚

**定义**：代码变更前的 diff 校验、测试门禁、失败回滚策略。

**证据检索**：
- pre-commit、CI pipeline
- 自动化测试覆盖变更模块
- 版本回滚或 feature flag 机制

**不适用于当前项目**：若项目定位为运行时 Agent 平台而非 Coding Agent 自动改码系统，应标注并说明边界。

---

### 11. AI 辅助开发流程

**定义**：Cursor Skill、Rules、自动化审查、开发闭环沉淀。

**证据检索**：
- `.cursor/skills/`
- `.cursor/rules/`、`agent.md`
- hooks、自动化脚本

---

### 12. 权限、安全和审计

**定义**：鉴权、敏感操作拦截、审计日志、SQL 表白名单。

**证据检索**：
- `guardrails/`、`risk_triage/`
- `ALLOWED_TABLES`、SQL 执行校验
- API 鉴权中间件

---

### 13. 大型代码仓库理解与跨模块修改

**定义**：多包/多模块结构下的影响面分析、跨目录一致性改动。

**证据检索**：
- 项目目录结构、`docs/README.md` 索引
- 跨模块 import 关系
- 模块化边界文档

## 状态打标标准

| 状态 | 判定条件 | 报告写法 |
|------|----------|----------|
| **已完整支持** | 实现 + （测试 或 文档）+ 可在主链路中触发 | 「已实现于 `path`，测试见 `test_path`」 |
| **部分支持** | 有核心实现，缺测试/文档/边界/观测中任一项 | 明确列出缺什么 |
| **缺失** | 在约定检索范围内无任何实现证据 | 「未找到实现」 |
| **有实现但缺少验证** | 有代码，无对应测试、benchmark、失败案例 | 「有 `path` 但无测试覆盖」 |
| **不适用于当前项目** | 与项目定位冲突 | 说明为何不适用，避免硬凑 |
| **待验证** | 检索不充分或证据模糊 | 「已在 X/Y 范围检索，未找到明确证据，建议人工确认 Z」 |

## 证据强度分级

写报告时为每条证据标注强度：

| 级别 | 标准 | 示例 |
|------|------|------|
| A | 直接实现 + 测试或文档 | `coverage_resolver.py` + 单测 |
| B | 有直接实现，无测试 | `fallback_to_text_to_sql` 有代码无测 |
| C | 仅文档/设计，无实现 | `plans/` 中的 roadmap |
| D | 未找到 | 标注检索过的路径 |

**禁止**：将 C 级证据标为「已完整支持」；将 D 级标为「缺失」（应标「待验证」除非检索充分）。

## 去重规则

合并为同一题当满足任一条件：
- 核心考察点相同（如都问「tool 失败怎么办」）
- 答案结构可共用（同一模块、同一设计决策）
- 一家公司变体是另一家子集

保留格式：
```
【合并】工具调用失败如何恢复？
  - 来源：快手.md Q3, 海天.md Q7
  - 主维度：工具失败恢复
```

## 优先级评分参考

每项改进打 1～5 分（越高越优先），加权求和：

| 因子 | 权重 | 5 分 | 1 分 |
|------|------|------|------|
| 面试频率 | 30% | 3+ 家公司都问 | 仅 1 次出现 |
| 短板明显度 | 30% | 缺失或完全无验证 | 仅表达不清 |
| 实现成本 | 20% | 1～3 文件小改 | 需架构重构 |
| 依赖阻塞 | 20% | 阻塞其他 3+ 项 | 无依赖 |

- 加权 ≥ 4.0 → P0
- 加权 2.5～3.9 → P1
- 加权 < 2.5 → P2

可因「面试临近」人工上调，须在报告中注明理由。
